# 望遠鏡に天文台ができた —— OrbitLens Ace を公開する

![Cover](https://raw.githubusercontent.com/machuz/eis/main/docs/images/blog/hatena/cover-ace-launch.png?v=1)

*望遠鏡は観測する。しかし観測は、読まれるのを待っている。*

---

## 何が起きたか

[EIS（Engineering Impact Signal）](https://github.com/machuz/eis)は望遠鏡だ。`git log` と `git blame` を読み、7軸と3軸トポロジーでエンジニアリングを観測し、結果を JSON で出すOSSのCLI。外部APIもAIトークンもいらない。git の地層にすでに刻まれているものを、ただ読む。

望遠鏡は宇宙を観測する。けれど、届いた光そのものは、何を観ているのかまでは教えてくれない。

今日、その望遠鏡に天文台ができた。**[OrbitLens Ace](https://ace.orbitlens.io)** を公開する。

---

## 境界 —— 望遠鏡と天文台

EIS と Ace は別の計器だ。そして、この二つを分けておくことに意味がある。

**EIS は望遠鏡だ。** 観測する。git にすでに記録されたものを読むだけで、それ以上のことはしない。推薦も、予測も、推論もしない。リポジトリに向ければシグナルが返る。誰が構造を形作ったか、誰のコードが生き残ったか、重力がどこにあるか。方法論は完全に公開され、すべての式が[ホワイトペーパー](https://github.com/machuz/eis/blob/main/docs/whitepaper.md)にある。分解できる望遠鏡だ。

**Ace は天文台だ。** 解釈する。EIS のシグナルの上に、構造を言葉として読み取る。散文の Structural Summary。チームの境界がモジュールの境界と一致しているか（コンウェイの法則）の検証。どのモジュールが静かに脆くなっているかの地図。そして、コードベースが何をくぐってきたかの組織年表。

望遠鏡は光を集める。天文台は空を読む。

なぜ分けておくのか。それは、天文台が自分の鏡を歪めないのと同じ理由だ。解釈を信頼できるものにするには、観測がきれいなままでなければならない。シグナルを集める計器が、そのシグナルの意味まで決めてしまったら、どこまでが観測でどこからが意見なのか、もう見分けがつかなくなる。Ace が天文台であることに誠実でいられるように、EIS は望遠鏡のままでいる。

---

## 天文台は何を読むのか

### Structural Summary —— 光を言葉に

EIS は数字を出す。けれど、コンテキストのない数字は危険だ。Survival が低いのは設計が弱いからかもしれないし、レガシーコードを書き換えている最中だからかもしれない。Ace はシグナルの場を読み、散文として描く。点数ではなく、何が立っていて何が立っていないかの記述として。

### コンウェイの法則の検証 —— 人とモジュールを突き合わせる

組織図はこう言う。モジュールの境界はああ言う。Ace は EIS のエンジニアトポロジーをモジュールトポロジーの隣に置き、両者がどこで一致しどこでずれているかを観る。サービスを所有しているチームが、実際にそれを書いているチームなのか。あるいは、知識が組織図の気づかないどこかへ静かに移ってしまっているのか。それが見えてくる。

### モジュールトポロジー + 崩壊リスク

健全なモジュールもある。脆いモジュールもある。良いから残っているのではなく、誰も触らないから残っているだけのモジュールだ。Ace は、変更圧が高くアクティブなオーナーがいないモジュールや、バスファクターが1のモジュールを浮かび上がらせる。リスクは常に git 履歴の中にあった。天文台は、それが危機になる前に観測可能にする。

### 組織年表 —— ここが芯だ

ここが最も大事な部分なので、それが何であって何でないかを、はっきりさせておきたい。

組織年表は**得点表ではない**。エンジニアを序列化しない。記録するのは、コードベースが何をくぐってきたかだ。生き延びたマイグレーション、ある subsystem を形作って去っていったアーキテクト、オーナーが変わった後に脆くなったモジュール。構造的な出来事の記録であり、チームが自分の歴史を振り返って見覚えを持てるように書かれている。

これは意図してこう作った。エンジニアリング指標の最も典型的な失敗は、それが評価に変えられてしまうことだ。名前の横の数字が、序列づけと罰のために使われる。EIS は設計でそれに抗う（時間減衰 survival は忙しさでは膨らまない）。Ace はその抵抗を引き継ぐ。**組織年表が観測するのは、コードベースが何をくぐってきたかであって、各人がどれだけ優秀かではない。** スコアは、もっと近くで観たいときに手に取るレンズへと格下げされる。決して見出しにはならない。

評価ではなく観測。得点表は人がゲームの仕方を覚えるもので、年表はチームが愛着を持つものだ。

## 始め方

扉は二つ、宇宙は同じ。

**望遠鏡（オープンソース）:**

```bash
brew install machuz/tap/eis
cd your-repo
eis analyze .
```

アカウント不要、連携不要。どんなリポジトリにでも向けて、自分でシグナルを読む。

**天文台（SaaS）:**

> [ace.orbitlens.io](https://ace.orbitlens.io)

GitHub アカウントを繋げば、Ace が観測を継続的に回し、あなたの代わりにそれを読む。Structural Summary、コンウェイ検証、崩壊リスク、そして年表。

---

## 望遠鏡は無料だ。ずっと。

望遠鏡である EIS は、完全に無料で、オープンソースのままだ。席数の制限も、トライアルの時計も、肝心な部分だけ壁の向こうに置く "open core" もない。方法論はすべて[ホワイトペーパー](https://github.com/machuz/eis/blob/main/docs/whitepaper.md)にあり、バイナリは `brew install` ひとつで手に入る。望遠鏡を開いておくこと自体が目的だ。誰でも自分のコードに向けて、こちらに何も尋ねずにシグナルを読める。

アイデアに課金したいわけではない。アイデアに広がってほしいだけだ。エンジニアリングは git から観測できること、生存は活動より長く残ること、静かな構造の仕事が見えないままでいるのはおかしいこと。壁の向こうに置かれたアイデアは、遠くまで行かない。

値段を持つのは天文台、つまり SaaS の Ace のほうだ。観測を継続的に回して読み返すことが、実際のインフラだからだ。壁にするためではなく、手が届くように値付けした。

- **Free** —— $0。ソロ開発者、あるいは5人までのチーム。公開リポは無制限、非公開はいくつか、履歴は6ヶ月。
- **Pro** —— $7/月。一人の開発者、全期間の履歴、完全な Gravity Certificate。
- **Nova** —— $39/月 base（8席込）＋ $18/席（9席目〜）。コンウェイ検証、崩壊リスク、メンバー別の所有といった組織レベルの読みを観たい非公開組織に。

対比してみる。エンジニアリング分析の多くは開発者ごとの課金で、だいたい開発者一人あたり月 $15〜50 の範囲、"contact sales" の向こうにあることも多い。Ace の組織プランは最初の8席まで base のフラット、その下の計器は無料だ。より少ないチームがより多く払うより、より多くのチームが自分のコードベースを観られるほうがいい。

そして人と一緒に旅をする痕跡である Gravity Certificate は、どのプランでも mint も検証もずっと無料だ。自分の仕事を証明するのに、お金はかからないほうがいい。

## なぜこの形なのか

望遠鏡だけでは観測しかできない。けれど観測だけでは、エンジニアの働く日々は変わらない。観測を読み、その中の構造に気づき、チームが自分の歴史を、動けるくらいはっきりと観られるようにする必要がある。

弧は端から端までつながっている。望遠鏡が観測し、天文台が解釈し、コードベースを静かに支えている人の仕事が、見えないままではなくなる。

光はずっと git の中にあった。今、それを読む計器ができた。

---

## 人を測ることについて —— そして、お願い

ずっと抱えている失敗のかたちがある。エンジニアリングを上から測った瞬間、つまり経営の高度から、組織が国家のように人を見渡すように測った瞬間に、現場にいる人が肌で感じている感覚は平らになっていきがちだ。数字が届くと、その人が実際に何をしたかの手触りが、その下に隠れてしまう。

その逆を作ろうとしている。そして、できているとは言い切れない。シグナルはシグナルであって、判定ではない。git に映らないものは測らないままにして、それを測れないと声に出して言うほうを選ぶ。メンタリング、コミットにならなかった設計の議論、障害のときに誰かが保っていた落ち着き。望遠鏡が届かないと知っている dark matter だ。低いシグナルは、小さな貢献ではない。多くの場合それは、その人ではなく組織についてのシグナルだ。

人を測るのは、善意でも危うい。現場が自分の仕事に対して持っている感覚を、一度も貶さずに測る方法を、見つけられたとはまだ思っていない。だからこれは本当のお願いだ。自分のシグナルを、あるいはチームのシグナルを読んで、何かが違うと感じたら、教えてほしい。平らにされた、不公平だ、本当に大事だったものが抜けている。そう感じたとき、その隙間こそ、計器がよくならなければいけない場所だ。
